Build the selective per-phase execution machinery (the F3 gap, D-12 — the largest single cost in the phase). From a cold USB-Mode start, artifacts marked Rebuild must run ONLY their corresponding build phase (Drivers, AppsISO, or DeployISO) in isolation, then hand the freshly built outputs to USB assembly alongside reused artifacts. Implements REBUILD-02, REBUILD-03, and decisions D-04 (buildable set incl. DeployISO), D-07 (Drivers input gating + degradation), D-08/D-09 (FFU never rebuilt here — only Drivers/AppsISO/DeployISO are rebuildable in USB Mode), and D-12 (the selective-execution capability).

This is the second of two BuildFFUVM.ps1 edits; it depends on plan 04 (the Disposition gate and AppsISO copy variables must already exist).

CRITICAL ordering (RESEARCH Pitfall 1 + 6, and BLOCKER-1): (a) the normal default-init block (~lines 2050-2090) runs AFTER the USBOnlyMode `return` (~line 1924), so a compact mini path-init MUST set $AppsISO/$AppsPath/$DeployISO/$PEDriversFolder/$DriversFolder/$adkPath before any rebuild call; (b) the DeployISO rebuild MUST run before the ISO mountability pre-check so the mount test validates the rebuilt ISO; and (c) the ENTIRE rebuild-execution block (Drivers/AppsISO/DeployISO) MUST appear at a LOWER line number than the plan-04 Disposition gate (`$dispositionCheckTypes`) so rebuilt artifacts reconcile their copy variables BEFORE the Skip/copy gate reads them — otherwise a Skip default could suppress a rebuilt artifact (BLOCKER-1).

Purpose: This is what makes "Rebuild" real — selective phase execution without corrupting the Full Build checkpoint state and without invoking VM/VHDX/OS machinery.
Output: Modified BuildFFUVM.ps1 (USBOnlyMode mini-init + rebuild flag set + selective rebuild execution block) and a structural ordering assertion appended to USBOnlyMode.Tests.ps1.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| config Disposition=='Rebuild' -> build-phase invocation | A Rebuild disposition triggers execution of a real build phase (New-AppsISO/New-PEMedia/driver download). |
| $driversJsonPath / Make / Model from config -> driver download | Config-sourced driver inputs drive a network/file download phase. |
| $adkPath (Get-ADKPath) -> oscdimg.exe invocation | ADK tool path feeds ISO creation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-50-10 | Elevation of Privilege | Rebuild must not execute arbitrary artifacts | mitigate | Only three fixed, trusted build functions are reachable (New-AppsISO, New-PEMedia, the existing Invoke-ParallelProcessing driver-download path). The block invokes named project functions — it never executes a user-supplied artifact file. Anti-pattern guard: no VM/VHDX/OS/Windows-ISO machinery is called from the USB-Mode block. |
| T-50-11 | Tampering | Disposition=='Rebuild' from config | mitigate | Rebuild gate uses an exact `-eq 'Rebuild'` comparison with PSObject existence check; any other value does not enable rebuild. Plan-04 enum validation already normalizes unknown values to Reuse before this runs. |
| T-50-12 | Denial of Service | ADK missing / driver path missing | mitigate | Null-check $adkPath and Test-Path $driversJsonPath; on failure the phase degrades (flag set false + warning) and USB assembly continues — a missing dependency cannot crash the whole USB-Mode run (Pitfall 5). |
| T-50-13 | Tampering | $driversJsonPath path injection | accept | Path is consumed by the existing, already-hardened driver-download machinery (not newly written here); reused as-is. Low risk: local desktop, user-owned config. |
| T-50-SC | Tampering | npm/pip/cargo installs | accept | No package installs; New-AppsISO/New-PEMedia use ADK's oscdimg.exe resolved via Get-ADKPath. |
</threat_model>
