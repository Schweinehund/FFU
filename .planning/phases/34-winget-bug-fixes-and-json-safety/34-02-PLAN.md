  <action>
Fix the path quoting in the "Build final command/arguments" section of Add-Win32SilentInstallCommand (currently lines 714-725).

**Understanding the execution context:**
Install-Win32Apps.ps1 uses `ProcessStartInfo.FileName` for CommandLine and `ProcessStartInfo.Arguments` for Arguments. When FileName contains spaces, it needs quotes. When Arguments contains a path with spaces (MSI /i), it needs embedded quotes.

**EXE fix (line 716):**
Current: `$silentInstallCommand = "$basePath\$resolvedRelativePath"`
This stores an unquoted path like `D:\win32\7-Zip File Manager\7z2301-x64.exe` — ProcessStartInfo.FileName can handle this since it resolves the path, BUT the path is assembled from `$basePath` which is `D:\win32\$AppFolder` where `$AppFolder` can contain spaces.

The actual fix: Wrap the EXE path in quotes so ProcessStartInfo.FileName handles it correctly:
```powershell
$silentInstallCommand = "`"$basePath\$resolvedRelativePath`""
```

**MSI fix (line 720):**
Current: `$silentInstallSwitch = "/i `"$basePath\$resolvedRelativePath`" $silentInstallSwitch"`
The backtick-escaped quotes ARE present, but they produce literal `"` characters in the string which is correct for msiexec arguments. However, verify this works by checking what the JSON serialization produces. The backtick-escaped double quotes in PowerShell (`"`) produce literal quote characters in the resulting string, which is exactly what msiexec expects: `/i "D:\win32\My App\installer.msi" /quiet`.

The MSI quoting is actually correct as-is. The real issue is that when `$silentInstallSwitch` was previously assigned from YAML parsing, it might be empty/null, causing the string to end with a trailing space. Add a Trim():
```powershell
$silentInstallSwitch = "/i `"$basePath\$resolvedRelativePath`" $silentInstallSwitch".Trim()
```

**Default case fix (line 724):**
Current: `$silentInstallCommand = "$basePath\$resolvedRelativePath"`
Same issue as EXE — wrap in quotes:
```powershell
$silentInstallCommand = "`"$basePath\$resolvedRelativePath`""
```

**Summary of changes:**
- Line 716 (EXE): Add backtick-escaped quotes around the full path
- Line 720 (MSI): Add `.Trim()` to remove trailing whitespace when $silentInstallSwitch is empty
- Line 724 (default): Add backtick-escaped quotes around the full path

Do NOT modify any other part of the function. The mutex changes from Plan 01 should already be in place.

<task type="auto">
  <name>Task 2: Verify JSON serialization preserves quotes correctly</name>
  <files>FFUDevelopment/FFU.Common/FFU.Common.Winget.psm1</files>
  <action>
Verify that the path quoting from Task 1 survives JSON round-trip (ConvertTo-Json then ConvertFrom-Json in Install-Win32Apps.ps1).

PowerShell's ConvertTo-Json escapes embedded double quotes as `\"` in JSON, which ConvertFrom-Json correctly deserializes back to `"`. This means:
- A CommandLine of `"D:\win32\My App\setup.exe"` (with literal quotes) serializes to `"\"D:\\win32\\My App\\setup.exe\""` in JSON
- When deserialized, it becomes `"D:\win32\My App\setup.exe"` again
- ProcessStartInfo.FileName receives this WITH the wrapping quotes

However, ProcessStartInfo.FileName actually strips leading/trailing quotes automatically on Windows. So `"D:\win32\My App\setup.exe"` and `D:\win32\My App\setup.exe` both work as FileName values. The quotes are actually not needed for ProcessStartInfo.FileName.

**Correction to Task 1 approach:** After further analysis, ProcessStartInfo.FileName handles unquoted paths with spaces correctly on Windows (it's the command-line/cmd.exe that needs quotes). The EXE CommandLine does NOT need wrapping quotes since Install-Win32Apps.ps1 uses ProcessStartInfo directly.

BUT: The path `D:\win32\$AppFolder` uses the raw `$AppFolder` name. If someone were to use this CommandLine in a cmd.exe context (which some orchestration scripts may do), quotes are still safer.

**Final decision:** Keep the EXE quoting from Task 1 as a defensive measure. It works correctly either way because ProcessStartInfo strips quotes, and if used in cmd.exe context, the quotes are necessary.

No additional code changes needed in this task — this is a verification-only task. Read the file, confirm the quoting from Task 1 is in place, and verify the module imports cleanly.

If any issues are found during verification, fix them in-place.
