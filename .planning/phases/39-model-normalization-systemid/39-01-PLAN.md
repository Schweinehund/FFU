  <name>Task 1: Dell model name normalization using GroupManifest Display CDATA</name>
  <files>FFUDevelopment/FFUUI.Core/FFUUI.Core.Drivers.Dell.psm1</files>
  <action>
Modify `Get-DellDriversModelList` to extract model names using the `GroupManifest/Display` CDATA text from the Dell catalog XML, with fallback to the existing `Model/Display` CDATA approach. This prevents duplicate brand prefixes like "Dell Dell Latitude".

**Implementation details for the XmlReader streaming parser:**

1. Track additional XML elements in the streaming parser: When inside a `SoftwareComponent` with `ComponentType value='DRVR'`, look for `SupportedSystems/Brand` elements. Within each `Brand` element:
   - Read the `Brand/Display` CDATA to get the brand name (e.g., "Dell")
   - For each `Model` child element, read `Model/Display` CDATA for raw model name AND look for a sibling `GroupManifest/Display` CDATA for the preferred display name

2. **GroupManifest Display extraction logic** (matching upstream commit `667edf3`):
   - If `GroupManifest/Display` CDATA exists, strip "PDK Catalog for " prefix (case-insensitive), trim the result, and use as model name
   - If GroupManifest not available, fall back to constructing model name from Brand Display + Model Display with StartsWith dedup:
     - If model name already starts with brand name (case-insensitive), use model name as-is
     - Otherwise, prepend brand name: `"$brandName $modelName"`

3. **Adaptation to our XmlReader architecture:**
   - The current parser uses `$isDriverComponent`, `$isModelElement`, and `$modelDepth` tracking
   - Add tracking variables: `$currentBrandName`, `$isGroupManifestDisplay`, `$groupManifestDisplayDepth`
   - When processing `Brand` element: capture Display CDATA as `$currentBrandName`
   - When processing `Model` element within a driver component: track both `Model/Display` and sibling `GroupManifest/Display` CDATA
   - **Key**: GroupManifest is a sibling of Model within Brand, not a child of Model. Read the `ReadSubtree()` approach instead: For each Brand element, use `ReadSubtree()` to process all children, capturing brand name, and for each Model, capturing both Model/Display and GroupManifest/Display
   - Actually, since the current first-pass parser iterates through ALL nodes sequentially, the simplest approach is: switch from the sequential CDATA-capture pattern to using `ReadSubtree()` for each `SoftwareComponent` that has `ComponentType value='DRVR'`. This is the approach already used in the second pass of `Save-DellDriversTask`. Extract Brand/Display, Model/Display, and GroupManifest/Display from the subtree DOM.

4. **Approach** (recommended for reliability): Refactor the first-pass model list extraction to use `ReadSubtree()` per SoftwareComponent (matching the approach already proven in `Save-DellDriversTask`):
   ```
   while reader.Read():
     if Element 'SoftwareComponent':
       subtree = reader.ReadSubtree()
       doc = XmlDocument.Load(subtree)
       if doc has ComponentType value='DRVR':
         for each Brand in SupportedSystems:
           brandName = Brand/Display/InnerText.Trim()
           for each Model in Brand:
             groupManifest = Model.SelectSingleNode("GroupManifest/Display")
             modelDisplay = Model.SelectSingleNode("Display")
             if groupManifest:
               name = groupManifest.InnerText -replace '(?i)^PDK Catalog for\s+', ''
               name = name.Trim()
             else:
               rawModel = modelDisplay.InnerText.Trim()
               if rawModel starts with brandName (case-insensitive):
                 name = rawModel
               else:
                 name = "$brandName $rawModel"
             uniqueModelNames.Add(name)
       subtree.Dispose()
   ```

5. Log normalization showing before/after when GroupManifest differs from raw Model/Display: `WriteLog "Dell model normalized: '$rawModelDisplay' -> '$finalModelName' (via GroupManifest Display)"`

6. Also update the model matching logic in `Save-DellDriversTask` to use the same GroupManifest-aware approach. When checking `$modelMatch`, also check GroupManifest/Display text (stripped of "PDK Catalog for" prefix) against the target model name, in addition to the existing Model/Display check. This ensures that models listed via GroupManifest can be found when downloading drivers.

**What NOT to do:**
- Do NOT create a generic cross-OEM normalization function — normalization is OEM-specific at catalog parse time (per CONTEXT.md decisions)
- Do NOT modify Lenovo handling — no brand prefix duplication observed (per CONTEXT.md)
- Do NOT change Save-DellDriversTask's download/extraction logic — only the model matching needs GroupManifest awareness

<task type="auto">
  <name>Task 2: Build-time SystemID/MachineType extraction in Update-DriverMappingJson</name>
  <files>FFUDevelopment/FFU.Common/FFU.Common.Drivers.psm1</files>
  <action>
Enhance `Update-DriverMappingJson` to extract and store SystemID (Dell/HP) or MachineType (Lenovo) for each driver mapping entry. Also update the DriverMapping.json schema to include these optional fields.

**Implementation details:**

1. **Dell SystemID extraction** (build-time, from model name string):
   - Regex pattern: `\(([^)]+)\)\s*$` — extracts the parenthesized suffix from model name strings (e.g., "Dell Latitude 7490 (ABC1)" -> "ABC1")
   - Normalize to `.Trim().ToUpperInvariant()`
   - Store as `SystemId` property on the mapping entry
   - If no parenthesized suffix found, `SystemId` = `$null` (logged, non-throwing)

2. **HP SystemID extraction** (build-time, from PlatformList.xml):
   - Add a helper function `Get-HPSystemIdFromPlatformList` (or inline scriptblock, implementer's choice — CONTEXT.md says Claude's discretion):
     ```
     param([string]$ModelName, [string]$DriversFolder)
     ```
   - Load PlatformList.xml from `$DriversFolder\HP\PlatformList.xml`
   - If file doesn't exist, attempt download from `https://hpia.hpcloud.hp.com/ref/platformList.cab`, expand, parse
   - If download/parse fails: log message + return `$null` (non-throwing per CONTEXT.md)
   - **3-tier matching** to find SystemID for the model:
     1. Exact case-insensitive match on ProductName text
     2. Stripped-to-alphanumeric match (both model name and ProductName stripped to `[A-Za-z0-9]` only)
     3. Contains match (ProductName contains model name or vice versa)
   - Return first matching Platform's `SystemID` element text, normalized with `.Trim().ToUpperInvariant()`
   - Use a per-call `[hashtable]` cache: parse PlatformList.xml once, build hashtable of ProductName -> SystemID, reuse for all HP entries in the batch
   - Store as `SystemId` property on the mapping entry

3. **Lenovo MachineType extraction** (build-time, from model name string):
   - Same regex as Dell: `\(([^)]+)\)\s*$` — extracts parenthesized suffix (e.g., "ThinkPad T14s (21BR)" -> "21BR")
   - Normalize to `.Trim().ToUpperInvariant()`
   - Store as `MachineType` property on the mapping entry
   - If no parenthesized suffix found, `MachineType` = `$null` (logged, non-throwing)

4. **Update-DriverMappingJson changes:**
   - Accept new optional parameter `[string]$DriversFolder` — wait, it already has `$DriversFolder`. Good.
   - Within the `foreach ($driver in $DownloadedDrivers)` loop, after determining Make/Model:
     - If Make is "Dell": extract SystemId via regex from Model
     - If Make is "HP": extract SystemId via PlatformList.xml lookup (build cache on first HP entry)
     - If Make is "Lenovo": extract MachineType via regex from Model
   - When creating `$newEntry` PSCustomObject, add `SystemId` and/or `MachineType` properties (set to `$null` if not applicable or extraction failed)
   - When updating `$existingEntry`, also update SystemId/MachineType if they've changed or were previously null
   - Log extractions: `WriteLog "[Dell] Extracted SystemId '$systemId' from model '$modelName'"` (or similar for HP/Lenovo)

5. **DriverMapping.json schema update:**
   - Existing schema: `{ Manufacturer, Model, DriverPath }`
   - New schema: `{ Manufacturer, Model, DriverPath, SystemId?, MachineType? }`
   - `SystemId` present for Dell and HP entries (or `$null`)
   - `MachineType` present for Lenovo entries (or `$null`)
   - Both properties are optional — `$null` values will be omitted from JSON by ConvertTo-Json

6. **Add Get-HPSystemIdFromPlatformList to Export-ModuleMember** — export it so tests can call it directly. Use the existing Export-ModuleMember line at the bottom of FFU.Common.Drivers.psm1.

**Error handling pattern (CONTEXT.md decisions):**
- All extraction failures: log message + set field to `$null`, never throw
- HP PlatformList.xml download failure: `WriteLog "WARNING: Could not download HP PlatformList.xml for SystemID extraction: $($_.Exception.Message)"` + cache `$null`
- HP PlatformList.xml parse failure: `WriteLog "WARNING: Could not parse HP PlatformList.xml: $($_.Exception.Message)"` + return `$null`
- No match in PlatformList.xml: `WriteLog "HP SystemID not found in PlatformList.xml for model '$modelName'"` + return `$null`

**What NOT to do:**
- Do NOT halt the build over a missing SystemID or failed extraction
- Do NOT create a module-level PlatformList.xml cache — per-call hashtable cache is sufficient (CONTEXT.md deferred)
- Do NOT extract SystemID for manufacturers other than Dell, HP, Lenovo (Phase 42 scope)
