Add three internal helper functions to FFUUI.Core.Drivers.Dell.psm1, placed before the existing `Get-DellDriversModelList` function. These are UI-layer duplicates of the build-layer functions added in Plan 40-01, following the existing pattern where UI and build modules have independent implementations.

**Function 1: Get-DellCatalogIndex**

Same signature and logic as the build-layer version (Plan 40-01 Task 2), but adapted for the UI context:
- Uses `Start-BitsTransferWithRetry` directly (UI layer does not use `Get-CachedOEMCatalog` from FFU.Drivers.psm1)
- Uses `Invoke-Process -FilePath "Expand.exe"` for cab extraction (matches existing pattern at line 74)
- Cache check: if `CatalogIndexPC.xml` exists and is less than 7 days old, return cached path
- On failure: log WARNING, return `$null`
- URL: `https://downloads.dell.com/catalog/CatalogIndexPC.cab` (hardcoded, matching existing `$catalogUrl` pattern at line 25 which also hardcodes URLs)

**Function 2: Get-DellClientModels**

Same signature and logic as Plan 40-01 Task 3. Uses XmlReader streaming with ReadSubtree() to parse `SystemConfiguration` elements from CatalogIndexPC XML. Returns `[System.Collections.Generic.List[PSCustomObject]]` with Make/Model/SystemId/CabUrl properties.

**Function 3: Resolve-DellCabUrlFromModel**

Same signature and logic as Plan 40-01 Task 4. Extracts SystemID from model display name via regex `'\(([0-9A-Fa-f]{4})\)\s*$'`, looks up in CatalogIndexPC models, returns cab URL or `$null`.

**Note:** These are duplicate implementations by design (per CONTEXT.md decision: "UI layer gets its own duplicate parsing -- matches existing pattern"). The UI cannot import from FFU.Drivers.psm1 because that module requires FFU.Core and other build-layer dependencies not available in the UI context.

  <name>Task 2: Update Get-DellDriversModelList to use CatalogIndexPC</name>
  <files>FFUDevelopment/FFUUI.Core/FFUUI.Core.Drivers.Dell.psm1</files>
  <action>
Modify `Get-DellDriversModelList` (starts at line 9) to use CatalogIndexPC for WindowsRelease <= 11, with fallback to the existing CatalogPC.cab approach.

**Current flow (lines 21-80):** Always downloads and parses CatalogPC.cab (or Catalog.cab for Server).

**New flow for WindowsRelease <= 11:**

1. **Try CatalogIndexPC first:**
   ```
   $indexXml = Get-DellCatalogIndex -DriversFolder $DriversFolder
   if ($null -ne $indexXml) {
       $indexModels = Get-DellClientModels -CatalogIndexPath $indexXml
       if ($indexModels.Count -gt 0) {
           # Success: return index-based models (already have SystemId + CabUrl)
           WriteLog "Using CatalogIndexPC: found $($indexModels.Count) Dell models"
           return $indexModels
       }
   }
   WriteLog "WARNING: CatalogIndexPC approach failed. Falling back to CatalogPC.cab for model list."
   ```

2. **Fallback to CatalogPC.cab:** Existing code (lines 21-217) runs as-is, but models from CatalogPC.cab will NOT have SystemId/CabUrl properties (they are populated only from CatalogIndexPC).

**Key changes to model object construction:**

For CatalogIndexPC-sourced models, the objects already have `Make`, `Model`, `SystemId`, `CabUrl` from `Get-DellClientModels`.

For CatalogPC.cab fallback models (lines 208-215), preserve the current structure:
```powershell
[PSCustomObject]@{
    Make  = $Make
    Model = $modelName
}
```
These lack SystemId/CabUrl, which is fine -- they'll be resolved at build time or populated on next CatalogIndexPC refresh.

**Windows Server path (WindowsRelease > 11):** Unchanged. CatalogIndexPC has no Server variant. The existing `$catalogBaseName = "Catalog"` path (line 22-25) continues as-is.

**Important:** The early return for CatalogIndexPC success means the CatalogPC.cab code is never reached when CatalogIndexPC works. This is the primary performance gain (avoid downloading/parsing 160MB).
